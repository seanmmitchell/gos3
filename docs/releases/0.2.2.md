# gos3 0.2.2

gos3 is an S3-compatible object storage server with an embedded or standalone
web console. It supports filesystem and remote S3 backings, IAM and bucket
policies, versioning and Object Lock, backing replicas, encryption, copy and
mirror jobs, and restic backup and recovery. v0.2.2 improves the safety of
those jobs and backups, adds a console relay for servers the browser cannot
reach directly, and updates the Go toolchain for a standard-library security
fix.

[Download v0.2.2](https://github.com/seanmmitchell/gos3/releases/tag/v0.2.2)
or read the [full changes since v0.2.1](https://github.com/seanmmitchell/gos3/compare/v0.2.1...v0.2.2).
The [0.2.0 overview](0.2.0.md) describes the full feature set and upgrades
from 0.1.0.

## Changes since 0.2.1

- **Safer copy and mirror jobs.** Resuming a job rechecks conflicts and
  cycles. Jobs bind to the original source and target bucket instances, so
  they stop if a bucket was deleted and recreated under the same name. For
  native S3 buckets, submission and each pass check the remote bucket's
  creation date and stop if the service cannot provide a verifiable identity.
  Copy and replication walks stop explicitly on a key with more than 4,096
  versions or delete markers instead of growing memory without bound.
- **Bounded restic reads.** Ranged GETs restore only the requested bytes.
  The new static `restic.restore_spool_bytes` limit caps encrypted restore
  spool reservations across backings and defaults to 1 GiB.
- **Policy and tag checks.** S3 tag writes reject keys that differ only in
  case, ambiguous existing tags fail closed for IAM conditions, and
  service-level administration honors accepted all-wildcard admin ARNs.
- **Console relay.** A connected gos3 server can relay console traffic to
  another server that the browser cannot reach. The browser still signs for
  the destination; the relay requires separate `admin:ProxyRequest` access,
  verifies uploaded bodies before forwarding, and does not automatically
  retry writes. A relay error after a write can leave its outcome unknown,
  so check the destination before retrying. S3 uploads use a payload-bound
  signature valid long enough for slow transfers and retain upload progress.
  Relayed PDFs download as attachments because browser PDF viewers do not
  reliably enforce the relay's sandbox restrictions.
  See the [web console relay guide](../web-ui.md) for setup and limits.
- **Build security and documentation.** The minimum Go version is 1.26.10
  to include the `crypto/x509` fix reported by `govulncheck`. The repository
  and release guides now reflect public source and signed provenance for
  newly built releases; the older v0.2.0 artifacts remain unattested.

## Install 0.2.2

| Distribution | Choose |
|---|---|
| Binary with console | `gos3_0.2.2_<os>_<arch>.tar.gz` (`.zip` on Windows) |
| Headless binary | `gos3_0.2.2_<os>_<arch>-headless.tar.gz` (`.zip` on Windows) |
| Container with console | `ghcr.io/seanmmitchell/gos3:0.2.2` |
| Headless container | `ghcr.io/seanmmitchell/gos3:0.2.2-headless` |

Archives cover Linux, macOS and Windows on amd64 and arm64; images cover
Linux amd64 and arm64. Both image variants include restic. Install restic
separately beside a binary if you use restic-backed storage or backups.
Follow the [quick start](../../README.md#quick-start) or the
[deployment guide](../deployment.md). Source builds require Go 1.26.10 or
newer; building the console also requires Node.js 22 and pnpm.

Check the archive against `checksums.txt` and verify its signed build
provenance, or verify an image and pin the verified digest. For example:

```sh
gh attestation verify gos3_0.2.2_linux_amd64.tar.gz \
  --repo seanmmitchell/gos3 --source-ref refs/heads/main
gh attestation verify oci://ghcr.io/seanmmitchell/gos3:0.2.2 \
  --repo seanmmitchell/gos3 --source-ref refs/heads/main
```

## Upgrading from 0.2.1

1. Stop writes and back up backing data, metadata, settings, credentials,
   encryption keys and restic repositories. Keep that backup available for
   rollback. See the [backup guide](../operations.md#backups).
2. Review copy and mirror jobs before upgrading. Jobs created before bucket
   instance binding was introduced stop on resume and must be resubmitted.
   Native bucket jobs also require the remote service to return a verifiable
   bucket listing and creation date; check that capability before relying on
   these jobs.
   If a key has more than 4,096 versions or delete markers, remove old
   versions before copying or replicating that key.
3. If you use restic-backed objects, size `restic.restore_spool_bytes` for
   your full-object reads. Reads larger than the limit return
   `ServiceUnavailable` until you raise it; ranged reads reserve only the
   requested range. The default is 1 GiB. The setting is static, so restart
   after changing it.
4. Upgrade the binary or image, restart, confirm `gos3 version` and
   `/_gos3/ready`, and test a signed upload and read. For browser relay
   access, configure an eligible gos3 connection, grant
   `admin:ProxyRequest`, allow the browser origin through CORS, and provide
   temporary disk space for uploads. Existing console connections remain
   direct until a relay is selected.

When upgrading from 0.1.0, also follow the
[0.2.0 upgrade checklist](0.2.0.md#upgrading-from-010), including its
storage-format and rollback cautions. A backup is the reliable rollback path
if an older build cannot read data written by a newer one.

## Limits to plan around

gos3 remains pre-1.0. Servers have independent namespaces; discovery and
the console relay do not make them one cluster. Backing replicas and mirror
jobs do not replace backups. Native S3 buckets inherit the remote service's
capabilities. There is no STS/session-token, AWS KMS, SSE-C or distributed
erasure-coding support. The relay requires network access and authorization
from its server to the destination, plus temporary disk for uploaded bodies;
it cannot guarantee whether a failed write reached the destination. Relayed
PDFs download instead of opening in the browser. See the
[compatibility reference](../s3-compatibility.md) and
[security guide](../security.md) before deploying.
