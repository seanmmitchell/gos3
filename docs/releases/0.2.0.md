# gos3 0.2.0

**v0.2.0 is the first full gos3 release:** an S3-compatible object storage
server with a web console, local and remote storage, replication, encryption
and backup tools in one Go binary. It builds on the initial v0.1.0 release
with storage management and recovery features, more deployment choices and
security fixes across the server, web UI and release pipeline.

gos3 remains pre-1.0 software: minor releases may change configuration,
the admin API or storage formats. Review the upgrade steps before replacing
an existing installation.

[Download v0.2.0](https://github.com/seanmmitchell/gos3/releases/tag/v0.2.0)
or read the [full changes since v0.1.0](https://github.com/seanmmitchell/gos3/compare/v0.1.0...v0.2.0).

## What you can do with gos3

- **Use existing S3 clients.** AWS CLI, AWS SDKs, `mc` and rclone can use
  gos3's endpoint with SigV4 and path-style addressing. The API supports
  multipart uploads and copies, checksums, presigned URLs, browser POST
  uploads, ranges, conditional requests, tags and canned ACLs.
- **Manage access and protect versions.** Root and IAM users, access keys,
  identity and bucket policies, Block Public Access, versioning, delete
  markers, Object Lock retention and legal holds, and lifecycle expiration
  are available through the API and web console.
- **Manage several servers from a browser.** The console includes an object
  browser, uploads, versions, metadata, share links, policies, storage,
  jobs, backups and metrics. It is embedded at `/_gos3/ui/` or can run
  standalone to manage several gos3 and other S3 endpoints. Discovery is
  available when explicitly enabled.

See the [README client examples](../../README.md#using-gos3-with-s3-clients)
and [S3 compatibility reference](../s3-compatibility.md) for supported
operations and differences from AWS.

## New since 0.1.0

### Storage backings and remote S3

A server can use several filesystem, memory and S3 backings, choose placement
per bucket, move buckets online and replicate them in active-passive or
active-active mode with automatic failover. Backings can be configured live
from the console.

An S3 backing connects an account on AWS S3, MinIO, R2 or another compatible
service. **Wrapped buckets** keep gos3's data and metadata in remote bucket
prefixes and provide gos3 storage features. **Native buckets** use remote
objects as they are, preserving access from other tools and passing through
the service's versioning and Object Lock capabilities. Administrators can
browse remote buckets and adopt existing ones.

See [backings](../backings.md) and
[placement and replication](../operations.md#multiple-backings-and-replication).

### Compression, encryption and backups

Transparent, seekable DEFLATE compression can be selected per bucket or
enforced or disabled server-wide. Native SSE-S3 uses authenticated
AES-256-GCM encryption for object data, including upload staging and multipart
parts on filesystem and wrapped S3 storage. Encryption keys and restic
repositories follow each bucket copy's backing.

Restic can archive each write or make scheduled whole-bucket snapshots with
retention and pruning. Recovery is available through gos3 and plain restic;
the `gos3 restic` commands can also work offline from configuration and
backings. Whole-bucket snapshots include native buckets.

See [compression](../operations.md#compression) and
[encryption, archives and snapshots](../encryption.md).

### Copy and mirror jobs

Persistent jobs copy a bucket or prefix once, or keep an independent target
mirrored, across backings and native/wrapped bucket kinds. They handle
versions, metadata, retention and bucket configuration according to the
selected options, report progress and conflicts, support pause/resume and
recover after restarts. To copy to another server, connect it as an S3
backing. See [jobs](../jobs.md), including their encryption and retention
safety rules.

### Deployment and management

JSON joins YAML, environment variables and CLI flags as configuration
options. The management API and embedded UI can be disabled independently;
headless archives and images omit UI assets. MinIO-style startup arguments,
credential aliases and health probes help with migration, but MinIO admin
APIs and disk layouts are not supported. Discovery now defaults to off.

The console adds live backing configuration, remote bucket adoption,
placement, jobs and backup management, settings submenus and Markdown table
previews. See [server modes](../configuration.md#server-modes) and
[the web UI](../web-ui.md).

### Security and release integrity

This release fixes authorization and Object Lock bypasses, rechecks
credentials and permissions on writes, bounds request and policy evaluation
work, and hardens recovery, remote version targeting, discovery and restic
trust boundaries. Force deletion respects legal holds and COMPLIANCE
retention, including for root; GOVERNANCE bypass requires an explicit request
and permission.

Release builds use pinned inputs, build the tagged commit without restored
caches, and publish checksums and image provenance/SBOMs. **Historical note:**
v0.2.0 was built while gos3 was private, so its archives and images have no
GitHub attestations. gos3 is now public, and new builds publish signed GitHub
attestations; this does not change the existing v0.2.0 artifacts. See
[security](../security.md) and [release verification](../releasing.md#verifying-a-release).

## Install 0.2.0

| Distribution | Choose |
|---|---|
| Binary with console | `gos3_0.2.0_<os>_<arch>.tar.gz` (`.zip` on Windows) |
| Headless binary | `gos3_0.2.0_<os>_<arch>-headless.tar.gz` (`.zip` on Windows) |
| Container with console | `ghcr.io/seanmmitchell/gos3:0.2.0` |
| Headless container | `ghcr.io/seanmmitchell/gos3:0.2.0-headless` |

Archives cover Linux (`linux`), macOS (`darwin`) and Windows (`windows`),
each for amd64 and arm64. Container images cover Linux amd64 and arm64.
Headless builds keep the management API; add `serve --no-admin` for S3-only
operation. Both container variants include restic. Binary installations
need a separate restic executable for restic features; native SSE-S3 needs
no restic executable.

Follow the [README quick start](../../README.md#quick-start) or
[deployment guide](../deployment.md). Start a downloaded binary with
`gos3 serve --data ./data` (`.\gos3.exe` on Windows). The startup banner
identifies the endpoints and credential source. Use generated or private
root keys, then create narrowly scoped IAM users for applications.

## Upgrading from 0.1.0

1. **Back up before starting 0.2.0.** Stop writes and preserve all backing
   data, metadata, IAM state, settings, encryption keys and restic repositories
   needed for recovery. Follow the [backup guide](../operations.md#backups).
   Restore the backup if rollback requires a format the old version cannot read.
2. **Review discovery and saved settings.** New defaults disable discovery,
   advertising, mDNS, beacons and scans. Explicit configuration and saved
   settings retain their values in managed mode. Enable each required switch;
   `--no-admin` ignores saved runtime settings and uses static configuration.
3. **Check credentials, policies and proxies.** Published example root secrets
   are refused. Bucket policy user principals must use local user names;
   AWS IAM user ARNs fail closed for non-root requests until corrected.
   Replace access keys that collide with user or reserved names. Configure
   `server.trusted_proxies` explicitly before relying on forwarded headers.
   See [security](../security.md).
4. **Plan for existing objects and rollback.** Enabling compression or
   encryption does not rewrite stored versions. Older builds cannot read
   compressed record format 4 or encrypted record format 5. Preserve keys
   and all versions required by retention; follow the
   [rollback instructions](../operations.md#upgrades).
5. **Verify, replace and restart.** Check `checksums.txt` for the archive and,
   when available, verify its GitHub attestation. For images, verify the
   provenance and pin the digest where available. Upgrade the binary or
   image, install restic if needed, restart, check `gos3 version` and
   `/_gos3/ready`, and confirm a signed upload/read with an application key.

Source builds require Go 1.26.9 or newer. Embedded/standalone UI builds use
Node.js 22 and the pnpm version pinned in `web/package.json`; headless builds
require only Go. Users of intermediate development builds should also read
the [S3 backing migration notes](../backings.md#migration-from-earlier-development-builds).

## Limits to plan around

- Servers are independent. Replicas belong to a single server's backing
  configuration; discovery does not create a cluster or shared namespace.
  Copy/mirror jobs can reach another server through S3, with mirror lag.
  Replication and mirroring do not replace independent backups.
- Native buckets inherit the remote service's capabilities and cannot be
  moved or replicated as gos3 bucket replicas; use copy/mirror jobs instead.
  Wrapped storage requires the remote service to support conditional writes.
- Memory storage is ephemeral and keeps object data in process memory;
  it does not provide at-rest encryption.
- There is one account and shared bucket namespace, with no STS/session
  tokens, distributed erasure coding, AWS KMS or SSE-C. Lifecycle transitions
  and S3 replication configurations are stored but not executed; gos3's
  backing replicas and mirror jobs are separate features.

See the [complete compatibility reference](../s3-compatibility.md) and
[operations guide](../operations.md) before relying on a particular API,
retention or recovery workflow.
